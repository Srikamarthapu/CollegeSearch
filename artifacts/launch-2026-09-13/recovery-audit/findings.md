# Recovery follow-up finding ledger

September 13, 2026. Baseline source: `07672e6603fe43980fbb5923d9c05fe348a746c1` (current application; later documentation-only commit `d056e10606db527713499bbb9a890fd15c98b592`).

1. **Confirmed: failed recovery discards the retained draft.** Both applicant-profile and deadline-plan `useSaved()` methods delete the tab recovery journal before reading the canonical browser copy. With a previously established conflict, a canonical read exception or malformed JSON then returns an empty unavailable/invalid snapshot. A synthetic Storage regression failed four of ten cases, proving loss of both the editable draft and journal while the canonical record remains untouched. This is direct store fault-injection evidence, not a real browser permissions failure. Preserve the journal and draft until the canonical copy is readable and valid.
2. **Confirmed: an aborted profile clear can be announced as complete.** While clear waits for its lock, another update can be reconciled into a newer nonempty ready snapshot. The store returns that unchanged ready snapshot; the component treats any ready result as “Profile cleared from this browser.” Synthetic lock-delay evidence proves the newer profile is still present. Add an explicit completion outcome and use it for the action message while preserving the snapshot's real status.

3. **Code-confirmed: recovery and file-read focus need ownership guards.** Successful profile/planner recovery removes its action row without a focus destination. Planner backup parsing unconditionally requested preview focus after awaiting a file read. Persistent storage-status targets now receive focus only when the clicked recovery button disappeared and focus has not moved elsewhere. File import captures focus before reading and checks it again before focusing the preview. Closed, hidden, inert and unmounted targets are excluded. The interrupted async branches are code-reviewed; no real browser storage failure or delayed file-read behavior is claimed.

Positive browser evidence: a stale deadline edit was rejected after another tab saved the same task. Error focus moved to the explanation; the original form survived reload and could be kept as a new task. This does not prove collection-level conflict or storage failure behavior by itself.

Fixes, regression results and the matching private deployment are recorded in REPORT.md and deployment.json. The full school launch goal remains open.

4. **Saved-list removal focus gap.** During hosted expiry QA, removing a college unmounted its focused card and left focus on the page. Source review confirms the removal handler has no focus destination. Keyboard Enter reproduced the same issue on the private guest shelf: Davis was removed, Irvine remained, and document.activeElement was BODY. The bounded repair targets the next Remove control, the previous control when removing the final card, or the empty shelf’s Explore link, guarded by scope, interactivity and retained focus ownership. The guest shortlist was empty before this follow-up.
